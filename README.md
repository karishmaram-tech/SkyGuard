# ✈ SkyGuard — Flight Delay Analytics & Risk Prediction

SkyGuard is an end-to-end data analytics and machine-learning application that
ingests the U.S. domestic flight records from 2015, predicts per-flight delay
risk, detects structurally anomalous route patterns, and delivers plain-English
operational briefings generated by Google Gemini — all presented through a
four-page interactive Streamlit dashboard.

---

## Business problem

Flight delays cost U.S. airlines an estimated **$8 billion per year** in direct
operating costs (crew overtime, fuel burn, gate holding) and erode passenger
satisfaction across millions of affected travellers. Operations teams need
answers to three questions before each day's schedule is locked:

1. **Which flights are most likely to be late?** — so buffer time can be added
   proactively.
2. **Which routes are behaving anomalously right now?** — so network controllers
   can redirect resources before a delay cascade begins.
3. **What concrete action should I take?** — framed in plain language, not
   model output.

SkyGuard answers all three from a single dashboard, with no data-science
expertise required to operate it.

---

## Dataset

**2015 Flight Delays and Cancellations**  
Source: <https://www.kaggle.com/datasets/usdot/flight-delays>

The dataset is published by the U.S. Department of Transportation (DOT) /
Bureau of Transportation Statistics (BTS) and covers every domestic commercial
flight operated in the United States during calendar year 2015. It ships as
three CSV files:

| File | Rows | Description |
|---|---|---|
| `flights.csv` | ~5.8 million | One row per flight — times, delays, cause codes |
| `airlines.csv` | 14 | IATA code → full carrier name |
| `airports.csv` | 322 | IATA code → name, city, state, lat/lon |

---

## How the model works (plain language)

1. **Merge & clean.** The three CSVs are joined on airline and airport codes.
   Cancelled and diverted flights are set aside — they have no arrival delay to
   predict — and the remaining ~5.3 million *operable* flights are randomly
   sampled to 800,000 rows for efficiency.

2. **Build leak-free features.** Every feature is information that would be
   known *before* the flight pushes back from the gate: the scheduled hour,
   day of week, month, season, origin/destination airports, carrier, route
   distance, and — critically — each carrier's and each airport's *historical*
   on-time rate computed only from flights on earlier dates (an expanding
   window). Nothing from after the flight departs is used.

3. **Define the target.** A flight is labelled **Delayed = 1** when its actual
   arrival is 15 or more minutes late — the FAA / BTS official threshold.

4. **Train on the past, test on the future.** Models are trained on
   January–October 2015 and evaluated on November–December 2015 — a
   time-based split that mirrors real deployment: you always predict tomorrow
   using only yesterday's history.

5. **Three models, pick the best.** A Logistic Regression (linear baseline),
   Random Forest (non-linear ensemble), and XGBoost (gradient boosting) are all
   trained. The one with the highest ROC-AUC on the Nov–Dec test set is used for
   the dashboard's risk scores.

6. **Flag anomalous routes.** Separately, an Isolation Forest runs on daily
   route-level delay-rate aggregates. Routes whose recent 30-day delay trend
   deviates from their full-year norm are flagged — catching systemic problems
   that the per-flight model would not surface.

7. **Generate briefings.** For the top flagged routes, the computed facts
   (expected risk %, actual rate %, primary delay cause, sample size) are fed
   into a fixed prompt template and sent to the Gemini API, which returns a
   three-sentence plain-English operational briefing.

## 🚀 Deploy to Streamlit Community Cloud (free, no commands needed)

The pre-built `sample.parquet` and `models/` artifacts are already committed.
Streamlit Cloud clones the repo and starts the app — no training, no scripts.

### Step 1 — Push to GitHub

```bash
git init                        # skip if repo already exists
git add .
git commit -m "Initial SkyGuard deploy"
git remote add origin https://github.com/<your-username>/skyguard.git
git push -u origin main
```

> **GitHub file-size note:** all parquet files are under 50 MB individually,
> well within GitHub's 100 MB per-file limit. No Git LFS needed.

### Step 2 — Connect to Streamlit Cloud

1. Go to <https://share.streamlit.io> and sign in with GitHub.
2. Click **New app**.
3. Choose your repository and branch (`main`).
4. Set **Main file path** to `app.py`.
5. *(Optional)* Add your Gemini API key: click **Advanced settings → Secrets** and add:
   ```toml
   GEMINI_API_KEY = "your-key-here"
   ```
6. Click **Deploy**. The app is live in ~2 minutes.

The deployed app starts in **under 2 seconds** — it reads the committed
parquet files directly; no CSV processing, no model training.

## Running locally

**Prerequisites:** Python 3.9 or later, `pip`.

```bash
# 1. Clone the repository (parquet artifacts are included — no CSVs needed)
git clone https://github.com/<your-username>/skyguard.git
cd skyguard

# 2. Create a virtual environment
python -m venv .venv
source .venv/bin/activate         # Linux / macOS
# .\.venv\Scripts\Activate.ps1   # Windows PowerShell

# 3. Install dependencies
pip install --upgrade pip
pip install -r requirements.txt

# 4. (Optional) Set the Gemini API key — Page 4 works without it
export GEMINI_API_KEY="your-key-here"   # Linux / macOS
# $env:GEMINI_API_KEY = "your-key-here"  # Windows PowerShell

# 5. Launch the app — starts in under 2 seconds
streamlit run app.py
```

### Rebuilding the artifacts (only if you change the dataset)

```bash
# Place flights.csv, airlines.csv, airports.csv in the project root, then:
python prepare_data.py    # ~60 s — rebuilds sample.parquet
python train_models.py    # ~60 s — rebuilds models/
# Commit the updated parquet files and redeploy
```

## Limitations

- **2015 data only.** The dataset covers a single calendar year. Structural
  changes in the U.S. airline network since 2015 — mergers, new routes, post-COVID
  demand patterns — are not reflected. Predictions should not be applied to
  current operations without retraining on recent data.

- **Sampled to 800,000 rows.** The full ~5.3 million operable flights are
  down-sampled to 800k via uniform random sampling (fixed seed) to keep training
  time practical on a laptop or free Colab instance. Delay rates in the sample
  are statistically unbiased (±0.05 pp at a 20% base rate), but thin routes with
  fewer than 200 flights in the sample are excluded from the route-risk table.

- **No weather or ATC data.** The model uses only schedule-derived and
  historical-rate features. Real-time weather, NOTAM advisories, and ATC flow
  control programmes — the dominant drivers of same-day delay spikes — are absent.
  This limits precision on individual high-impact days.

- **Classification, not regression.** The model predicts whether a flight will
  be delayed (binary), not by how many minutes. Severity estimation would require
  a separate regression model on the delayed subset.

- **Gemini API latency and cost.** The AI Insights page makes a live API call
  per route. In high-traffic or batch scenarios, rate limits and per-token costs
  apply. Briefings are cached in `st.session_state` for the duration of a session
  but regenerated on restart.
